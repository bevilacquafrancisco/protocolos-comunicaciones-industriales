# 06 · Bus RS-485 y primer enlace MODBus (dispositivo 1 ↔ dispositivo 2)

**Objetivo:** el maestro de la Raspberry Pi sondea al ESP32 por el bus RS-485. Es la consigna 1: el
Dashboard muestra MODBUS = DONE, los contadores avanzan y el LED responde a los comandos.

**Requisitos:** el criterio de salida de 03 (ESP32 verificado) y el de 05 (servicio activo).
**Tiempo:** ~20 min.

---

## 1. Conexionado del bus

> ⚠️ Con la Raspberry Pi apagada (`sudo poweroff`, esperar a que el LED verde deje de parpadear) y el
> ESP32 desenchufado.

```
  Raspberry Pi 4 ──USB── Adaptador USB↔RS-485            ESP32 #1 + MAX485
                           A  ─────────────────────────────  A
                           B  ─────────────────────────────  B        (par trenzado)
                           GND ────────────────────────────  GND      (masa común)
```

| Conexión | Por qué |
|---|---|
| A con A, B con B, **en todos los nodos** | Invertirlos no daña nada, pero no hay comunicación (todo TIMEOUT) |
| **GND común** entre el adaptador y el ESP32 | RS-485 es diferencial, pero el transceptor tolera solo −7 a +12 V de modo común. Sin GND común, el potencial flota |
| A y B en par trenzado | El ruido se induce igual en los dos conductores y el receptor diferencial lo cancela |
| Sin terminación de 120 Ω mientras el bus mida < 1,5 m | 03 §4 y firmware/README.md §3.3 |

Encender: primero el ESP32 (USB a la notebook o a un cargador), después la Raspberry Pi.

## 2. Verificar que la Raspberry reconoce el adaptador

```bash
$ ls -l /dev/ttyUSB* /dev/serial/by-id/ 2>/dev/null
$ dmesg | grep -iE "ttyUSB|ch34|ftdi|cp210" | tail -5
```

Tiene que aparecer `/dev/ttyUSB0`, que es lo que espera la configuración de fábrica del maestro.

- Si aparece con otro número, porque hay más de un adaptador, se cambia desde el Dashboard (§3) por
  la ruta estable `/dev/serial/by-id/...`, que no cambia al reconectar.
- **Adaptador FTDI** (riesgo R-04, prueba B-4): leer
  `cat /sys/bus/usb-serial/devices/ttyUSB0/latency_timer`. Si da 16, el conversor agrupa los bytes
  cada 16 ms y eso infla `LatenciaMs`. Se anota y se mide antes y después de bajarlo a 1.

Reiniciar el servicio para que tome el puerto (no es necesario si ya reintentó solo):

```bash
$ sudo systemctl restart pdci-t3-nodered && journalctl -u pdci-t3-nodered -f
```

Ya no tiene que aparecer `serial port /dev/ttyUSB0 error`. A los pocos segundos tiene que aparecer
`Status.OPCUA.Estado = DONE`: el maestro está entregando datos frescos.

## 3. Verificación en el Dashboard

Con el túnel SSH abierto (05 §7), entrar a **http://localhost:1880/dashboard**.

| ✓ | Dónde | Esperado |
|---|---|---|
| ☐ | *Estadísticas → Estado de las cuatro capas* | MODBUS = **DONE**. `OK` sube unas 15 veces por segundo (ciclo de 262 ms, 4 lecturas). `CRC_ERROR`, `TIMEOUT` y `EXCEPTION` quietos |
| ☐ | *Estadísticas → Variables* | El pulsador cambia al presionarlo; el potenciómetro va de 0 a 4095 al girarlo, con el porcentaje |
| ☐ | *Estadísticas → Variables*: LED digital ON/OFF y LED PWM | El LED físico responde. El valor mostrado es el **confirmado** por la lectura siguiente (ADR-015) |
| ☐ | *Estadísticas → Tramas* | TX `01 02 00 00 00 01 B9 CA` y su RX con el CRC válido |
| ☐ | *Configuración → Probar conexión*: FC 04, dirección 0, cantidad 1 | Trama cruda de ida y vuelta, `CRC válido` |
| ☐ | Consola de Thonny del ESP32 | `latido: respondidas=` creciendo; `crc=0` e `invalidas=0` |

| Síntoma | Causa probable | Qué revisar |
|---|---|---|
| Todo **TIMEOUT**, el ESP32 no cuenta nada | A y B invertidos, o el bus no llega | Invertir A/B en un extremo; continuidad del par |
| TIMEOUT y el ESP32 cuenta `invalidas` | Baud rate o paridad distintos | Dashboard *Enlace*: 9600, paridad *none*, 8, 1, Unit ID 1 |
| El ESP32 cuenta `respondidas`, pero el maestro ve TIMEOUT | El maestro no recibe: falta la masa común, o el adaptador no conmuta la dirección | GND común; otro adaptador (R-04) |
| **CRC_ERROR** esporádicos | Ruido, falta de GND, o RO sin pull-up | 03 §2; GND común; acortar el bus |
| Bytes `00` espurios en la consola del ESP32 | Falta el pull-up de 680 Ω de RO | 03 §2 (incidente 4 de la T1) |

## 4. Reconfiguración en vivo (consigna 1.d, I-04)

En *Configuración → Enlace*, cambiar el Unit ID a 7 y tocar **Aplicar sin reiniciar**:

- a los ≈ 2 s, MODBUS pasa a **DEVICE NOT REACHED** (ausencia sostenida, ADR-014);
- al volver a 1, recupera **DONE** sin reiniciar nada.

Es la falla F-03, y demuestra que el maestro se reconfigura sin recompilar.
